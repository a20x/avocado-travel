# ADR-0011. Города — отдельная таблица, справочники правятся в админке

**Статус:** принято.

## Контекст

Замечание преподавателя по лабе 3: «Нет возможности добавить во всплывающие списки новых значений городов и авиакомпаний для ввода и поиска». Справочники заполнялись только сидом. Отдельной таблицы городов не было: город собирался из аэропортов с одинаковым `city_slug`, а падежные формы («из Москвы», «в Москву») и описания лежали в коде (`catalog-data/cities.ts`). Значит, новый город нельзя было завести без правки кода.

## Решение

- **Таблица `cities`**: адрес (`slug`, уникальный, не меняется), название, формы «из …» и «в …», страна, описание, иллюстрация. Аэропорт ссылается на город внешним ключом `airports.city_slug → cities.slug`. Колонки `airports.city` и `airports.country` удалены — у названия города одно место хранения.
- Для страниц и API ничего не меняется: тип `Airport` по-прежнему содержит `city` и `country`, репозиторий берёт их через JOIN с `cities`. В запросах других модулей, где нужно название города (`database`, `flights`, `booking`, `analytics`), добавлен JOIN с `cities`.
- **Админка**: разделы «Города», «Авиакомпании» (добавить, изменить, удалить) и «Рейсы» (завести рейсы по расписанию, по желанию с обратными; удалить маршрут без билетов). Запись меняет только сервис модуля-владельца: города и авиакомпании — `catalog-data`, рейсы — `flights`.
- Город и авиакомпанию с рейсами удалить нельзя: на рейсы ссылаются билеты и отчёты. Внешние ключи в базе страхуют это правило.
- Время в пути и цены рейсов из админки считаются по расстоянию теми же функциями, что и демо-расписание: они переехали из `db/seed/schedule.ts` в `src/modules/flights/schedule.ts`.
- Списки городов и авиакомпаний сортирует сервис по правилам русского алфавита (`localeCompare('ru')`): порядок строк в PostgreSQL зависит от настроек сервера.

## Альтернативы

- **Колонки «из …» и «в …» прямо в `airports`.** Меньше переделок, но название и формы города повторялись бы у каждого его аэропорта (у Москвы их три), а переименование пришлось бы делать в нескольких строках.
- **Оставить описания в коде, а в базе хранить только новые города.** Два источника правды: часть городов правится в админке, часть — только в коде.

## Последствия

- Миграция `0014` создаёт `cities`, переносит в неё 18 городов из аэропортов с формами и описаниями, затем удаляет колонки `city` и `country` у аэропортов. На боевой базе она применяется сама при запуске.
- Название города в запросах — через JOIN: на каждый аэропорт в запросе добавляется таблица `cities`.
- Сид заполняет `cities` первым: формы и описания городов теперь лежат в `db/seed/catalog-data.ts`.
