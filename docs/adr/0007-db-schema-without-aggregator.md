# ADR-0007. Схемы базы без общего сборщика

**Статус:** принято

## Контекст

Таблицы описываются в `schema.ts` своих модулей ([04-data-model.md](../04-data-model.md)). Первая версия архитектуры предполагала файл `src/server/db-schema.ts`, который собирает таблицы всех модулей в один объект для Drizzle, и настройку Better Auth в `src/server/auth.ts`.

Оба файла нарушают правило зависимостей из [03-architecture.md](../03-architecture.md): `src/server` не должен импортировать модули. Хуже того, получается цикл: модуль импортирует `server/db.ts`, тот — `db-schema.ts`, а тот снова модули. Циклы делают поведение зависимым от порядка загрузки файлов и размывают слои.

Общий объект со всеми таблицами нужен Drizzle для двух вещей: чтобы drizzle-kit нашёл таблицы для миграций и для краткого синтаксиса Relational Queries (`db.query.flights.findMany({ with: { airline: true } })`).

Отдельный вопрос — связи между модулями: рейс ссылается на аэропорт и авиакомпанию (`catalog-data`), заказ — на рейс и пользователя (`auth`), поиск рейсов делает `JOIN` с аэропортами.

## Решение

1. Файла `db-schema.ts` нет. drizzle-kit находит таблицы сам по маске `src/modules/*/schema.ts`, указанной в `drizzle.config.ts` в корне проекта. `src/server/db.ts` создаёт подключение без схем модулей.
2. Запросы пишутся построителем Drizzle (`db.select().from(...).innerJoin(...)`), а не через Relational Queries.
3. Настройка Better Auth живёт в модуле `auth` (`src/modules/auth/server/auth.ts`) рядом с его таблицами.
4. Модуль публикует свои таблицы через `index.ts`. Другие модули могут ссылаться на них во внешних ключах и читать их в своих репозиториях. Изменять данные чужого модуля — только через его сервис.

## Альтернативы

- **Оставить `db-schema.ts` с исключением в линтере.** Даёт синтаксис `with: {...}`, но цикл остаётся, а исключение в правилах границ придётся объяснять и поддерживать.
- **Вынести сборщик из `src/` (например, в `db/schema.ts`).** Линтер перестаёт видеть нарушение, но цикл никуда не девается.

## Последствия

- Правила `eslint-plugin-boundaries` остаются строгими, без исключений.
- Связи между таблицами пишутся явными `JOIN`, как в SQL. Это ближе к цели [ADR-0002](0002-postgresql-drizzle.md) — видеть, что происходит в базе, — и помогает в лабе 3.
- Правило «чужие таблицы только читаем» линтер не проверяет; оно держится на ревью.
- Если Relational Queries когда-нибудь понадобятся, решение пересматривается новым ADR.
