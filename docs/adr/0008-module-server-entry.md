# ADR-0008. Входы модуля: index.ts, ui.ts и server.ts

**Статус:** принято

## Контекст

Первая версия архитектуры открывала модуль снаружи только через `index.ts`. В нём оказались вперемешку чистый код (типы, таблицы, расчёт салона) и серверный (сервисы с доступом к базе, помеченные `server-only`). В задаче T-08 это сломало три вещи:

- модульным тестам чистой логики понадобилась база: импорт `seatCapacity` тянул за собой подключение к ней;
- drizzle-kit, загружая схему рейсов, загружал и серверный код соседнего модуля и падал на `server-only`;
- клиентский компонент (схема салона в T-11) не смог бы импортировать модуль вообще.

## Решение

У модуля до трёх публичных входов:

- `index.ts` — общий: типы, Zod-схемы, таблицы, чистые функции. Без React — безопасен где угодно, в том числе в браузере и в скриптах вне Next.js.
- `ui.ts` — компоненты из `ui/`. Данные они получают в пропсах, к базе не обращаются. Отдельный вход появился в T-09: когда компоненты экспортировались из `index.ts`, скрипт демо-данных, импортируя таблицы, тянул за собой `next/image` и падал.
- `server.ts` — серверный: сервисы. Начинается с `import 'server-only'`, поэтому импорт из клиентского компонента ломает сборку.

Внутренние файлы модуля по-прежнему закрыты. Правило проверяет `eslint-plugin-boundaries`: снаружи разрешены только `index.ts`, `ui.ts` и `server.ts`.

## Альтернативы

- **Оставить один вход и обходить проблемы.** Запуск drizzle-kit с флагом `--conditions=react-server`, фиктивная база в тестах. Обходы копятся, а клиентские компоненты всё равно не смогут пользоваться модулем.
- **Разрешить импорт любых файлов модуля.** Теряется граница модуля — главное правило архитектуры.

## Последствия

- Серверный код импортируется как `@/modules/<модуль>/server`, компоненты — как `@/modules/<модуль>/ui`, общий — как `@/modules/<модуль>`.
- Чистая логика тестируется без базы.
- Схемы загружаются drizzle-kit без обходных флагов.
- Так же устроены многие пакеты для Next.js: отдельная точка входа для сервера.
