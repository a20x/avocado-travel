# ADR-0012. Вторая копия сайта на alwaysdata с автоматической выкладкой

**Статус:** принято. Дополняет [ADR-0009](0009-hosting-render-neon.md): размещение на Render остаётся.

## Контекст

В ноябре 2026 года сайт на Render у автора стал открываться только через VPN. Точная причина не установлена; вероятно, это ограничения доступа из российских сетей к инфраструктуре Cloudflare, через которую работает Render. Преподаватель должен открывать сайт из России без VPN, а прежний адрес при этом должен продолжать работать.

Нужна вторая бесплатная площадка с Node.js и PostgreSQL. Выбран alwaysdata: бесплатный тариф без срока, Node.js, PostgreSQL, SSH и API для управления сайтом. Ограничения тарифа на момент выбора — 256 МБ памяти и 1 ГБ диска.

Первую выкладку делали вручную: архив сборки скачивали из GitHub Actions и загружали по SSH. Так каждое изменение приходится выкладывать руками, а распаковка поверх работающего каталога может смешать файлы двух версий.

## Решение

- **Копия, а не переезд.** Тот же код из `main` работает на Render и на alwaysdata. У каждой копии своя база: на alwaysdata — отдельная PostgreSQL, в которую один раз скопирована база Neon. Данные между копиями не синхронизируются.
- **Сборка — в GitHub Actions.** `next build` не помещается в 256 МБ памяти, поэтому workflow `.github/workflows/alwaysdata-deploy.yml` собирает standalone-сборку на серверах GitHub с адресом `https://avocado-travel.alwaysdata.net`.
- **Выкладка автоматическая, после CI.** Workflow запускается, когда CI на `main` прошёл. Архив отправляется по SSH, распаковывается в новый каталог релиза `~/apps/avocado/releases/<дата-время-коммит>`, ссылка `~/apps/avocado/current` переключается на него, а сайт перезапускается через API alwaysdata. Ручного подтверждения нет.
- **Проверка и откат.** Workflow ждёт, пока сайт начнёт отдавать статику новой сборки и `/api/health` ответит 200. Если за 3 минуты этого не произошло, ссылка возвращается на прошлый релиз и сайт перезапускается ещё раз.
- **Два прошлых релиза** хранятся для отката, более старые удаляются после успешной выкладки.
- Команды на сервере собраны в `scripts/alwaysdata-release.sh`, а доступы (ключ SSH, токен API) хранятся в секретах репозитория.

## Альтернативы

- **Скачивать архив и выкладывать вручную.** Так было при первой выкладке. Легко забыть обновить вторую копию, и нет отката.
- **Собирать на сервере (`git pull` и `pnpm build`).** Сборке не хватает 256 МБ памяти, а на сервер пришлось бы ставить pnpm и все devDependencies.
- **Копировать файлы поверх работающего каталога (`rsync`).** Пока идёт копирование, сервер видит смесь старых и новых файлов, а откат требует отдельной копии.
- **Перенести сайт целиком и отказаться от Render.** Прежний адрес уже знают, и с другими сетями он работает.

## Последствия

- Каждое слияние в `main` через несколько минут попадает на обе площадки. Миграции применяются при запуске на каждой базе отдельно (`DB_MIGRATE_ON_START=true`).
- Ключ SSH в секретах GitHub даёт доступ к серверу: ключ отдельный, только для выкладки, и отзывается без смены остальных.
- Новость, заказ или пользователь, созданные на одной копии, на другой не появятся.
- Workflow «Боевая база» работает только с базой Neon. Демо-данные на alwaysdata не загружаются автоматически.
- Резервную копию базы alwaysdata перед миграциями workflow не делает.
- Настройки сайта и переменные окружения на alwaysdata задаются в панели вручную, как описано в [09-deploy.md](../09-deploy.md#вторая-копия-на-alwaysdata).
