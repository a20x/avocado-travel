# 09. Публикация сайта

Как сайт работает в интернете, как его развернуть с нуля и как обновлять. Почему выбраны именно эти сервисы — [ADR-0009](adr/0009-hosting-render-neon.md).

## Где что работает

| Часть | Сервис | Бесплатный тариф |
|---|---|---|
| Сайт | [Render](https://render.com), Docker-образ из `Dockerfile` | 512 МБ памяти, 0,1 процессора, 750 часов в месяц — хватает на круглосуточную работу одного сайта |
| База | [Neon](https://neon.com), PostgreSQL | 1 ГБ (демо-данные занимают около 40 МБ), 100 часов работы базы в месяц; без запросов база засыпает через 5 минут |
| Расписание | [cron-job.org](https://cron-job.org) | Задания с любым интервалом от минуты, свои заголовки запроса |

Все три сервиса бесплатны без срока. Сайт и база — во Франкфурте: это ближайший к России регион, и запросы к базе идут внутри одного города.

Вторая копия сайта работает на [alwaysdata](https://www.alwaysdata.com) — `https://avocado-travel.alwaysdata.net`, со своей базой. Она обновляется автоматически из того же `main`, см. [«Вторая копия на alwaysdata»](#вторая-копия-на-alwaysdata) и [ADR-0012](adr/0012-second-copy-alwaysdata.md).

## Как устроен деплой

- **Образ.** `Dockerfile` собирает сайт в три этапа: зависимости, сборка (`next build` с `output: 'standalone'`), запуск. В итоговый образ попадают только сервер Next.js с нужными ему пакетами, статика и миграции — без исходников и devDependencies. Сервер работает не от root.
- **Сборке не нужны секреты.** На время `next build` проверка переменных в `src/server/env.ts` отключена: страницы с данными рисуются по запросу, в базу сборка не ходит. Нужен только `NEXT_PUBLIC_SITE_URL` — Next.js вписывает его в код (ссылки, `robots.txt`); Render передаёт переменные сервиса в сборку как аргументы.
- **Миграции применяются сами.** При запуске сервера `src/instrumentation.ts` проверяет переменные окружения и применяет новые миграции из `db/migrations` (в образе включено `DB_MIGRATE_ON_START=true`). Локально это выключено — там миграции запускает `pnpm db:migrate`.
- **Проверка перед переключением.** Render отправляет посетителей на новую версию, только когда `/api/health` ответил 200. Если переменных не хватает или миграция упала, сервер отвечает 500 — деплой помечается неудачным, а сайт продолжает работать на прежней версии.
- **Автоматический деплой.** После слияния PR в `main` и успешного CI Render сам собирает и выкладывает новую версию (`autoDeployTrigger: checksPass` в `render.yaml`). CI заодно собирает Docker-образ — сломанный `Dockerfile` виден ещё в PR.

## Расписание

Бесплатный сайт на Render засыпает после 15 минут без запросов, и первое открытие после этого ждёт около минуты. Преподаватель и робот Яндекса могут прийти в любое время, поэтому cron-job.org каждые 5 минут открывает служебную страницу `/api/health` — сайт не засыпает. Эта страница в базу не ходит, иначе будила бы и её и тратила бесплатные часы Neon.

| Задание | Адрес | Как часто |
|---|---|---|
| Не давать сайту заснуть | `GET /api/health` | каждые 5 минут |
| Автоотмена неоплаченных заказов | `POST /api/cron/expire-orders` | раз в час |
| Импорт новостей отрасли | `POST /api/cron/import-feeds` | раз в 6 часов |

У заданий `/api/cron/*` заголовок `Authorization: Bearer <CRON_SECRET>` — значение из настроек сервиса на Render.

Автоотмена на хостинге — раз в час, а не каждые 5 минут, как задумано в [03-architecture.md](03-architecture.md#задания-по-расписанию): каждое задание будит базу, и при запуске каждые 5 минут она не спала бы никогда — 100 бесплатных часов кончились бы за три недели. На правильность это не влияет: при открытии брони просроченный заказ и так считается недействительным.

Планировщик GitHub Actions не подошёл: он запускает задания с опозданием на 10–30 минут (сайт успевал бы заснуть) и отключает расписание в репозитории, где 60 дней не было коммитов.

## Первый деплой

Делается один раз. Нужен VPN: сайт Neon из России отвечает 403. Сама база для сайта на Render доступна, а вот с компьютера в России до неё не достучаться: без VPN провайдер обрывает защищённое соединение с серверами Amazon, а VPN обычно закрывает порт баз данных 5432. Поэтому базу заполняет GitHub Actions — на серверах GitHub таких ограничений нет.

### 1. База на Neon

1. Войти на [neon.com](https://neon.com) через GitHub, создать проект: регион **AWS Europe Central 1 (Frankfurt)**, PostgreSQL — последняя версия.
2. В настройках вычислений (Compute) поставить постоянный размер **0,25 CU** без автомасштабирования — так 100 бесплатных часов расходуются медленнее всего.
3. Скопировать строку подключения (Connection string, **без** галочки «Connection pooling») и заменить в конце `?sslmode=require&channel_binding=require` на `?sslmode=verify-full`.

### 2. Структура и демо-данные

1. На GitHub в репозитории: **Settings → Secrets and variables → Actions → New repository secret** — три секрета:
   - `PRODUCTION_DATABASE_URL` — строка подключения из шага 1;
   - `PRODUCTION_ADMIN_EMAIL` и `PRODUCTION_ADMIN_PASSWORD` — почта и пароль администратора сайта (свои, не из `.env.example`).
2. **Actions → «Боевая база» → Run workflow**, в поле «Что сделать» выбрать `seed`, нажать **Run workflow**.
3. Через 2–3 минуты у запуска должна появиться зелёная галочка. В журнале шага `pnpm db:seed` — «Демо-данные загружены», в шаге импорта — отчёт по лентам.

Workflow `.github/workflows/production-db.yml` умеет три вещи: `migrate` — только применить миграции, `seed` — миграции, демо-данные и новости отрасли, `import-feeds` — миграции и импорт новостей. Секреты GitHub не показывает в журналах, а запустить workflow может только владелец репозитория. Сид в конце собирает статистику таблиц (`ANALYZE`): без неё первые отчёты аналитики на новой базе строились почти минуту.

### 3. Сайт на Render

1. Войти на [render.com](https://render.com) через GitHub, **New → Blueprint**, выбрать репозиторий `avocado-travel` — Render прочитает `render.yaml`.
2. Заполнить переменные, которые Render спросит:
   - `DATABASE_URL` — строка подключения из шага 1;
   - `NEXT_PUBLIC_SITE_URL` — `https://avocado-travel.onrender.com` (если имя занято, Render даст другой адрес — тогда исправить переменную и выбрать **Manual Deploy → Deploy latest commit**);
   - `ADMIN_EMAIL`, `ADMIN_PASSWORD` — те же, что в шаге 2;
   - `NEXT_PUBLIC_YANDEX_METRIKA_ID` — пусто, заполняется в T-34.

   `BETTER_AUTH_SECRET`, `CRON_SECRET` и `IP_HASH_SALT` Render создаст сам, `CLIENT_IP_HEADER` уже указан в `render.yaml`.
3. Дождаться окончания первой сборки (5–10 минут) и открыть `https://<адрес>/api/health` — должно быть `{"status":"ok"}`.

### 4. Расписание на cron-job.org

Зарегистрироваться на [cron-job.org](https://console.cron-job.org/signup) и создать три задания из таблицы [«Расписание»](#расписание). Для `/api/cron/*`: метод POST, во вкладке **Advanced → Headers** — заголовок `Authorization` со значением `Bearer ` и `CRON_SECRET` из **Render → Environment**. Ответ 200 в журнале задания — всё работает; 401 — неверный секрет.

### 5. Проверка

```bash
pnpm check:russia https://avocado-travel.onrender.com
```

Скрипт открывает главные страницы с узлов [check-host.net](https://check-host.net) в российских сетях и печатает таблицу «страница × узел» — это отчёт о доступности из России (L1-09). Дальше — вход администратора, HTML главной на [validator.w3.org](https://validator.w3.org/nu/).

## Обновление

Обычный порядок: PR → CI → слияние в `main` → Render собирает и выкладывает новую версию сам, миграции применяются при запуске. Одновременно workflow «Сайт на alwaysdata» выкладывает ту же версию на вторую копию. Ничего запускать руками не нужно.

Демо-данные на боевой базе обновляются так же, как в шаге 2: workflow «Боевая база» с действием `seed`. Сид стирает заказы, отзывы и сообщения посетителей, поэтому без нужды его не запускать.

## Вторая копия на alwaysdata

Тот же код, отдельный сервер и отдельная база PostgreSQL на alwaysdata. Данные между копиями не синхронизируются: новость или заказ, созданные на одной, на другой не появятся. Почему так — [ADR-0012](adr/0012-second-copy-alwaysdata.md).

### Как устроена выкладка

Workflow `.github/workflows/alwaysdata-deploy.yml` («Сайт на alwaysdata») запускается сам, когда CI на `main` прошёл. Вручную — **Actions → «Сайт на alwaysdata» → Run workflow** (только с `main`).

1. Собирает сайт на серверах GitHub (на alwaysdata сборке не хватило бы 256 МБ памяти) и упаковывает standalone-сборку, статику, миграции и файлы лабы 2 в архив. Архив ещё 3 дня можно скачать из запуска.
2. По SSH отправляет архив на сервер и распаковывает его в новый каталог релиза.
3. Переключает ссылку `current` на новый релиз и перезапускает сайт через API alwaysdata. При запуске применяются миграции.
4. До 3 минут ждёт, пока сайт начнёт отдавать статику новой сборки и `/api/health` ответит 200. Получилось — удаляет старые релизы, кроме двух прошлых. Нет — возвращает `current` на прошлый релиз, перезапускает сайт и завершается с ошибкой.

Каталоги на сервере:

```text
~/apps/avocado/
├── current -> releases/20261104-153000-e06f6ef   # работающий релиз
└── releases/
    ├── 20261103-120000-6c7c928                   # два прошлых — для отката
    ├── 20261104-101500-1bdc81b
    └── 20261104-153000-e06f6ef
```

Команды на сервере — в `scripts/alwaysdata-release.sh`: workflow передаёт его по SSH, на сервере ничего ставить не нужно.

### Первая настройка выкладки

Делается один раз. Сайт на alwaysdata, его база и переменные окружения уже должны быть настроены.

1. **Ключ для выкладки.** На своём компьютере создать отдельный ключ и добавить его на сервер:

   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/avocado_deploy -N "" -C "github-actions avocado"
   ssh-copy-id -i ~/.ssh/avocado_deploy.pub ПОЛЬЗОВАТЕЛЬ@ssh-avocado-travel.alwaysdata.net
   ```

   Пользователь и сервер SSH — в панели alwaysdata, раздел **Remote access → SSH**.
2. **Ключ сервера**, чтобы workflow не отправил архив подменённому серверу:

   ```bash
   ssh-keyscan ssh-avocado-travel.alwaysdata.net
   ```

3. **Токен API:** в панели alwaysdata **Profile → Tokens**, создать токен. **ID сайта** — число в адресе страницы настроек сайта в панели (`…/site/<ID>/…`).
4. **Секреты репозитория** — **Settings → Secrets and variables → Actions → New repository secret**:

   | Секрет | Значение |
   |---|---|
   | `ALWAYSDATA_SSH_HOST` | Сервер SSH, например `ssh-avocado-travel.alwaysdata.net` |
   | `ALWAYSDATA_SSH_USER` | Пользователь SSH |
   | `ALWAYSDATA_SSH_KEY` | Закрытый ключ целиком: `pbcopy < ~/.ssh/avocado_deploy` |
   | `ALWAYSDATA_SSH_KNOWN_HOSTS` | Вывод `ssh-keyscan` из шага 2 целиком |
   | `ALWAYSDATA_ACCOUNT` | Имя аккаунта alwaysdata |
   | `ALWAYSDATA_API_TOKEN` | Токен из шага 3 |
   | `ALWAYSDATA_SITE_ID` | ID сайта из шага 3 |

5. **Первый релиз:** **Actions → «Сайт на alwaysdata» → Run workflow**. Он распакует сборку в `~/apps/avocado/releases/…`, создаст ссылку `current` и закончится сообщением «Первая выкладка». Сайт пока работает из прежнего каталога.
6. **Переключить сайт** в панели: **Web → Sites → сайт → изменить**:
   - Working directory — `/home/АККАУНТ/apps/avocado/current`;
   - Command — `node /home/АККАУНТ/apps/avocado/current/server.js`.

   Сохранить, перезапустить сайт и открыть `https://avocado-travel.alwaysdata.net/api/health` — должно быть `{"status":"ok"}`. Переменные окружения сайта не меняются.
7. Когда сайт проработал на новом каталоге хотя бы одну выкладку, прежний каталог ручной выкладки можно удалить: `rm -rf ~/apps/avocado-travel`.

Ключ `~/.ssh/avocado_deploy` нужен только GitHub: если он утёк, удалить его строку из `~/.ssh/authorized_keys` на сервере и повторить шаги 1 и 4.

### Переменные сайта на alwaysdata

Задаются в панели: **Web → Sites → сайт → Environment**. Значения секретов — свои, не те, что на Render.

| Переменная | Значение |
|---|---|
| `NODE_ENV` | `production` |
| `NEXT_PUBLIC_SITE_URL` | `https://avocado-travel.alwaysdata.net` — тот же, что в workflow |
| `DATABASE_URL` | Подключение к PostgreSQL на alwaysdata |
| `BETTER_AUTH_SECRET`, `CRON_SECRET`, `IP_HASH_SALT` | Случайные значения: `openssl rand -hex 32` |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | Администратор сайта |
| `DB_MIGRATE_ON_START` | `true` |
| `HOSTNAME`, `PORT` | Адрес и порт, которые панель показывает в настройках сайта |

Расписание — те же задания `/api/cron/*` на cron-job.org с адресом alwaysdata и его `CRON_SECRET`.

### Если выкладка не прошла

| Признак | Что делать |
|---|---|
| Шаг «Выложить» падает на `scp` или `ssh`, «Permission denied» или «Host key verification failed» | Проверить секреты `ALWAYSDATA_SSH_*`: ключ скопирован целиком, публичная часть есть в `~/.ssh/authorized_keys`, `ssh-keyscan` сделан для того же сервера |
| Ошибка `curl` при перезапуске, код 401 или 404 | Неверный токен, имя аккаунта или ID сайта |
| «Новая версия не ответила за 3 минуты» | Сайт уже возвращён на прошлый релиз. Причина — в журнале сайта: `~/admin/logs/sites/` или панель. Если ошибка в каждой выкладке — проверить, что сайт в панели запускается из `current` (шаг 6) |
| Нужно откатить вручную | По SSH: `ls ~/apps/avocado/releases`, затем `ln -sfn releases/<релиз> ~/apps/avocado/current` и перезапуск сайта в панели |

## Если что-то не так

| Признак | Где смотреть |
|---|---|
| Деплой неудачный | Render → сервис → **Events** и **Logs**: строка «Неверные переменные окружения» перечисляет, чего не хватает |
| Сайт открывается минуту | Задание `/api/health` на cron-job.org выключено или падает |
| Ошибки базы, «compute time quota exceeded» | Neon → **Monitoring**: кончились часы работы базы; проверить, что автоотмена — раз в час |
| Все посетители «с одного IP» (общий бан, общий лимит запросов) | `CLIENT_IP_HEADER=true-client-ip` в переменных Render |
| `pnpm db:migrate` с компьютера падает, «Connection terminated unexpectedly» или `ETIMEDOUT` | Это сеть, а не база: из России до Neon не достучаться. Пользоваться workflow «Боевая база» |
