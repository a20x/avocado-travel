# Документация Avocado Travel

Документация — главный источник правды о проекте. Код пишется по ней, а если в ходе работы решение меняется, сначала меняется документация, потом код.

| Файл | О чём | Когда читать |
|---|---|---|
| [01-requirements.md](01-requirements.md) | Требования методички по каждой лабе и чем они закрываются | Перед началом любой задачи, при сдаче лаб |
| [02-product.md](02-product.md) | Что за продукт: страницы, роли, сценарии, бизнес-правила | Когда делаешь страницу или функцию |
| [03-architecture.md](03-architecture.md) | Стек, модули, слои, правила зависимостей, структура папок | Перед написанием кода |
| [04-data-model.md](04-data-model.md) | Схема базы данных и демо-данные | Когда работаешь с базой |
| [05-api.md](05-api.md) | Публичный REST API, форматы выгрузки, ленты | Лаба 4, интеграции |
| [06-design.md](06-design.md) | Палитра, типографика, принципы интерфейса | Когда верстаешь |
| [07-conventions.md](07-conventions.md) | Стиль кода, Git, PR, тесты, критерии готовности | Всегда |
| [08-roadmap.md](08-roadmap.md) | Порядок реализации: этапы и задачи | Когда выбираешь следующую задачу |
| [09-deploy.md](09-deploy.md) | Публикация: хостинг, первый деплой, расписание, обновление | Когда выкладываешь сайт или он не открывается |
| [adr/](adr/) | Записи архитектурных решений: что решили и почему | Когда возникает вопрос «а почему так?» |

## Как вести документацию

- Документы пишутся простым языком: их должен понять разработчик, который видит проект впервые.
- Любое значимое решение (выбор библиотеки, отказ от требования, смена подхода) оформляется отдельным ADR в `docs/adr/`.
- Если код и документация расходятся, это баг. Исправляется в том же PR.
