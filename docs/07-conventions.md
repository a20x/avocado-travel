# 07. Соглашения

Правила, по которым пишется и принимается код. Цель — чтобы любой разработчик, открыв любой файл, сразу понимал, что в нём и почему.

## Код

### TypeScript

- Строгий режим (`strict`, `noUncheckedIndexedAccess`). `any` запрещён; если тип неизвестен — `unknown` и проверка.
- Типы выводятся из схем (Drizzle, Zod), а не дублируются руками.
- Функции сервисов возвращают результат вида `{ ok: true, data }` или `{ ok: false, error }` для ожидаемых ошибок. Исключения — только для неожиданных ситуаций.

### Именование

| Что | Как | Пример |
|---|---|---|
| Файлы компонентов | PascalCase | `SeatMap.tsx` |
| Остальные файлы | kebab-case | `price-calculator.ts` |
| Компоненты, типы | PascalCase | `FlightCard`, `SearchQuery` |
| Функции, переменные | camelCase | `findFlights`, `seatCount` |
| Константы | UPPER_SNAKE_CASE | `MAX_PASSENGERS` |
| Таблицы и колонки базы | snake_case | `forum_posts.created_at` |
| Коды ошибок | UPPER_SNAKE_CASE | `SEAT_TAKEN` |

Имена — на английском, понятные без комментария: `findAvailableSeats`, а не `getData2`.

### Комментарии

- Комментарий объясняет **почему**, а не **что**: «копейки, а не рубли — чтобы не было ошибок округления», а не «умножаем на 100».
- Публичные функции модулей (`index.ts`) — с коротким JSDoc.
- Тексты интерфейса и комментарии — на русском, код — на английском.

### Компоненты

- Серверные по умолчанию, `'use client'` — только при необходимости.
- Один компонент — один файл. Компонент больше ~150 строк — повод разделить.
- Никакой логики запросов в компонентах: данные приходят из сервиса через серверный родитель или action.

### Форматирование

Prettier форматирует автоматически, ESLint проверяет правила. Код, который не проходит `pnpm lint`, не попадает в `main`.

## Git

### Ветки

- `main` — всегда рабочая версия. Прямые пуши запрещены, только через PR.
- Одна задача — одна ветка: `feature/flight-search`, `fix/seat-double-booking`, `refactor/booking-service`, `docs/api`, `chore/ci-cache`.

### Коммиты

Формат [Conventional Commits](https://www.conventionalcommits.org/ru/):

```
feat(guestbook): скрытие записей со стоп-словами
fix(booking): двойная продажа места при одновременной брони
docs(api): описание выгрузки CSV
test(flights): тесты расчёта свободных мест
chore: обновление зависимостей
```

Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `style`, `chore`. В скобках — модуль. Описание — по-русски, с маленькой буквы, без точки.

### Pull Request

- Заголовок — в формате коммита.
- Описание по шаблону `.github/pull_request_template.md`: что сделано, как проверить, какие требования закрыты (коды из [01-requirements.md](01-requirements.md)), скриншоты для интерфейса.
- PR маленький и про одно. Больше ~400 изменённых строк — повод разделить.
- Слияние — **Squash and merge**, ветка удаляется.

## Тесты

- Каждое бизнес-правило сервиса покрыто модульным тестом. Тест лежит рядом с кодом: `service.ts` → `service.test.ts`.
- Название теста описывает поведение по-русски: `it('скрывает запись со стоп-словом')`.
- Сквозные тесты Playwright — для ключевых сценариев из [02-product.md](02-product.md#сценарии).
- Тесты не зависят друг от друга и от порядка запуска; база для интеграционных тестов очищается перед каждым набором.

## Критерии готовности задачи (Definition of Done)

Задача считается сделанной, когда:

- [ ] функциональность работает по описанию в документации;
- [ ] `pnpm check` проходит: типы, линтер, тесты, сборка;
- [ ] бизнес-правила покрыты тестами;
- [ ] HTML новых страниц валиден;
- [ ] интерфейс проверен на ширине 360 px и 1280 px;
- [ ] документация обновлена, если поведение отличается от описанного;
- [ ] CI в PR зелёный, ревью пройдено.

## Команды

| Команда | Что делает |
|---|---|
| `pnpm dev` | Запуск для разработки |
| `pnpm build` | Сборка |
| `pnpm lint` | ESLint |
| `pnpm typecheck` | Проверка типов |
| `pnpm test` | Модульные и интеграционные тесты |
| `pnpm test:e2e` | Сквозные тесты |
| `pnpm check` | Всё вместе — то же, что запускает CI |
| `pnpm db:up` / `db:down` | Запуск и остановка PostgreSQL в Docker |
| `pnpm db:generate` | Сгенерировать миграцию после изменения схемы |
| `pnpm db:migrate` | Применить миграции |
| `pnpm db:seed` | Заполнить демо-данными |
| `pnpm db:reset` | Пересоздать базу с нуля |
