# CLAUDE.md — правила работы в проекте Avocado Travel

Этот файл читается в начале каждой сессии. Документация в `docs/` — главный источник правды о проекте.

## Контекст

- Учебный проект по курсу «Web-программирование»: сайт продажи авиабилетов, один проект на все лабы семестра.
- Автор — студент, это его первый проект с нуля. Он учится по ходу работы.
- Требования методички с кодами — `docs/01-requirements.md`. Порядок работы — `docs/08-roadmap.md`.

## Как работать с автором

1. **Одна задача за раз.** Работаем строго по задачам из `docs/08-roadmap.md`, по порядку. Не начинай следующую задачу и не делай «заодно» то, что к текущей не относится.
2. **Перед задачей — короткий план и вопросы.** В начале задачи в нескольких строках опиши, что будешь делать, и задай вопросы, на которые документация не отвечает. Дождись ответов, затем выполняй задачу целиком, без остановок после каждого файла. Возникли вопросы по ходу — спрашивай сразу.
3. **Объясняй коротко, на русском.** После задачи — общая логика: что сделано, как части связаны, какие решения приняты и почему. Без построчного разбора файлов. Подробности — только если автор спросит.
4. **Работай в ветке задачи.** Перед началом убедись, что ты не на `main`; если на `main` — предложи создать ветку по правилам из `docs/07-conventions.md`.
5. **В конце задачи:** запусти `pnpm check`, покажи результат, предложи сообщение коммита в формате Conventional Commits и напомни открыть PR по шаблону.
6. **Если документация не покрывает ситуацию** или противоречит сама себе — остановись и спроси, а не додумывай. Если решение меняется — сначала обнови документацию.

## Архитектура — коротко

Подробно — `docs/03-architecture.md`.

- Модульный монолит: `src/app` (только адреса и сборка страниц) → `src/modules/<модуль>` → `src/shared`, `src/server`.
- Внутри модуля: `ui/` → `server/actions.ts` или API-маршрут → `server/service.ts` → `server/repository.ts` → база.
- Снаружи модуль доступен только через его `index.ts`.
- Чужие таблицы (из `index.ts` другого модуля) можно читать в своём `repository.ts`, менять — только через сервис модуля-владельца.
- Компоненты серверные по умолчанию, `'use client'` — только для интерактивности.
- Деньги — целые копейки. Время — `timestamptz` в UTC.

## Обязательно

- TypeScript strict, без `any`.
- Ввод проверяется Zod **на сервере**, права — на сервере в каждом action и маршруте.
- Запросы к базе — только в `repository.ts` и только через Drizzle.
- Бизнес-правила покрыты тестами Vitest рядом с кодом.
- Ожидаемые ошибки сервиса — результат `{ ok: false, error: 'КОД' }`, а не исключение.
- Секреты — только в переменных окружения; новая переменная добавляется в `.env.example` и `src/server/env.ts`.
- Изменил поведение — обнови документацию в том же PR.
- Перед использованием API Next.js сверяйся с документацией установленной версии в `node_modules/next/dist/docs/` — она новее твоих знаний.

## Запрещено

- Писать SQL или обращаться к базе из компонентов и маршрутов в обход сервиса.
- Импортировать внутренние файлы чужого модуля.
- `dangerouslySetInnerHTML` без санитайзера.
- Добавлять зависимость без объяснения, зачем она и почему не хватает существующих.
- Использовать настоящие названия авиакомпаний и их коды ИАТА (авиакомпании в проекте выдуманные).
- Копировать интерфейсные решения существующих сервисов продажи билетов — см. `docs/06-design.md`.
- Коммитить в `main` напрямую.
